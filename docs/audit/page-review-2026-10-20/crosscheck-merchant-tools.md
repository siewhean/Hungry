No app implementation, shared canonical document, provider data, simulator state or dependency was changed.

## Scope and method

Read `REVIEW_BRIEF.md`, `merchant.md`, `saved-tools.md`, actual referenced screens/components/stores/service handlers, feature flags and route registration, and relevant migration definitions plus searches for later replacements. Merchant report accounts for 16 assigned files; saved-tools report accounts for 20. The per-file tables cover those manifests; this pass concentrates on each finding's evidential chain rather than claiming a second full visual inspection of every rendered screen.

Production scope checked: `src/constants/featureFlags.ts` disables merchant centre, collections/checklists and group wheel; portfolios and solo wheel are enabled. `ProfileStack.tsx:85–108` confirms collections/checklists and portfolios are separately registered. Root merchant registration is conditional. Backend policies remain relevant independently of disabled mobile navigation, but live applied policy state and table grants were not inspected.

Adjudication terms: **Accepted** = supported source behavior/omission at the stated scope; **Narrowed** = core issue remains but claims or severity require qualification; **Unresolved** = source concern lacks sufficient proof. No successful deployed exploit or measured native symptom is implied by an accepted source finding. Native accessibility/layout, real two-account RLS, actual migration replay, mail delivery and device behavior remain separate acceptance work.

## Corrections that matter to the final report

1. **ST-01 is an overbroad source authorization boundary, not a demonstrated successful private-note read.** Authenticated whole-row item grants and visibility policy include `private_notes`, and the service requests `*`. However, the current source also contains a recursive policy graph (`portfolios` SELECT → `portfolio_collaborators` SELECT → `portfolios`). An ordinary query can fail policy expansion before returning any row. A permissive predicate cannot be reported as a measured live disclosure. Keep P1 remediation priority; test both query viability and private-field denial on the applied schema. Removing the recursion must not accidentally make the private-note exposure reachable.
2. **MER-02 and MER-27 have an earlier prerequisite:** the authenticated draft path is itself blocked by the checked-in draft RLS in MER-04. Their accept-before-edit/partial-commit defects remain in source, but do not assert that a normal current merchant has already published a draft through that denied path. If draft access is repaired or differs in the deployed schema, those downstream bugs become actionable.
3. **MER-24's delivery wording was too broad.** Weekly summary creates in-app notification rows, so saying no one has been notified merely because there is no email receipt is not established. The supported defect is that queued email work is represented as sent, invite status is written `sent` before worker delivery, and weekly recipients include pending invites (`inviteStatus !== 'removed'`), while copy says active team. Classify recipient/status accuracy as P2; treat demand for delivery receipts as an external verification gap, not proof of non-delivery.
4. **MER-14, MER-21, ST-08 and ST-13 contain conditional effects.** Source exposes races, overwrite effects and missing semantics; exact network timing, first-focus ordering, native clipping and assistive-technology outcomes still need reproductions. Avoid counting each hypothetical outcome as a separately confirmed bug.
5. **ST-10 is misleading publication semantics, not absence of user consent.** The user explicitly chooses Public. The defect is Draft/Publish labels suggesting a second public-release boundary that table/RPC reads do not enforce.
