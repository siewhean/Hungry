## Findings, ordered by severity

Independent cross-check qualifications: MER-02/27 are downstream of the draft-access/RLS mismatch in MER-04 and do not establish an ordinary merchant has successfully published through that path. MER-24 includes real in-app notification creation; email delivery is unknown, while premature sent status and pending-recipient inclusion are supported defects. MER-05/MD-PRIV-01 are one shared source privacy gap with no proven deployed disclosure. Full per-ID decisions: `crosscheck-merchant-tools.md`.

### P1 — primary tasks, data loss, or security boundaries

**MER-01 — Existing photo URLs make normal dish edits fail.** Class: confirmed source contract defect; gated-beta core editing blocker. `DishEditorScreen.tsx:99`, `:132`, `:278`; `src/lib/services/supabase/supabaseService.ts:2369` and `:442`. Trigger: open a dish whose image is HTTPS, change its price and save, paste a URL, or choose the signature photo. The editor always submits the loaded URL/gallery, but `resolveMerchantDishGalleryUrls` requires every URL to be a local device file. No local photo picker is offered in this screen. Thus the advertised flow throws before the dish update; mock success hides the mismatch. Recommendation: keep previously owned stored URLs without re-uploading, allow new photos through an actual local picker, and enforce ownership/source permission for changes. Owner: mobile + merchant service. Close: live-mode test saving unchanged owned photo, replacement local photo, removal, and rejected arbitrary remote asset; customer read-back.

**MER-02 — “Edit before adding” adds the dish before the editor opens.** Class: confirmed source/publishing-boundary defect; gated-beta. `OCRDraftScreen.tsx:87` and `:251`; Supabase service `:5377`. `handleEditDraft` calls `acceptOCRDraft`, creates a canonical dish, removes the draft, then navigates. Cancel/back does not undo it. A wrong OCR price/name can enter the menu before correction. This proves a catalog write, not that provenance-gated consumer surfaces necessarily display it. Recommendation: edit draft state first and accept atomically on explicit save. Owner: mobile + merchant service. Close: open/edit/back leaves draft pending and creates no dish; final save creates exactly one corrected dish.

**MER-03 — Rejected-verification resubmission contradicts the server immutability guard.** Class: confirmed checked-in client/SQL contract defect; gated-beta. Supabase service `:5085`; `supabase/migrations/0038_app_security_hardening.sql:196`; `VerificationCentreScreen.tsx:169`. Trigger: previously rejected verification with non-null rejection fields → upload replacement evidence. Upsert sets `rejected_at` and `rejection_reason` to null, while the merchant trigger forbids changing them. Evidence/storage may already have been written before the status update fails. Recommendation: controlled resubmission RPC permitting only the intended transition while preserving an audit trail; coordinate guard and client. Owner: backend + merchant service. Close: authenticated SQL integration test rejected→submitted, unchanged decision history, no self-approval; UI receives successful new status. Mock state-machine test passing does not prove this flow.

**MER-05 — Home-location privacy is stored as a preference with no demonstrated consumer redaction.** Class: confirmed source integration gap; privacy impact requires live cross-check. `HomeBasedVerificationScreen.tsx:187`; `BusinessProfileEditorScreen.tsx:595`; Supabase service `:5110` and `:5160`. Privacy is saved only to `merchant_outlets.location_privacy`; linked `venues` still retain unit/floor and consumer repository/detail paths do not consume `locationPrivacy`. Search of checked-in migrations/services found no redaction bridge. Trigger: linked home outlet chooses Hidden/Approximate, then a consumer reads its venue/location. Consequence: interface promises concealment without an evidenced enforcement path; do not claim a measured production leak. Recommendation: enforce visibility in authoritative public read projection/RPC, never rely on client hiding; define approximate location semantics. Owner: backend privacy + consumer detail/map. Close: different user and anonymous queries for exact/approximate/hidden assert address, unit/floor, coordinates, route/share payloads and cached reads. Root was asked to cross-check this independently.

**MER-28 — UI verification gate is absent from checked-in catalog write authorization.** Class: confirmed source authorization gap; live policy applicability unverified. `src/features/merchant/merchantGuards.ts:20`; `supabase/migrations/0020_merchant_rls_hardening.sql:6`; `0019_merchant_consumer_linkage.sql:93`; `0022_merchant_catalog_column_guards.sql:5`. An owner/manager of an unverified linked outlet is rejected by the mobile route gate but `merchant_can_manage_venue` / outlet-link helper only check ownership/role, without verification state. Later trigger definitions still call those helpers. Direct authenticated requests can therefore pass the checked-in catalog authorization model without the UI's verification requirement. This is scoped to the caller's linked venue, not an assertion of arbitrary cross-tenant access. Recommendation: central server capability predicate including verification/role/revocation, while preserving explicit draft verification writes. Owner: backend security. Close: migration replay and authenticated owner/manager/staff/unverified/rejected/revoked matrix for dish/profile/reply/promotion operations. Backend endpoints need assessment even while merchant UI is production-disabled.

**MER-29 — Later migration replaces provenance guards with weaker versions.** Class: confirmed source migration regression; deployment proof pending. `supabase/migrations/20260710133000_enrichment_cursor_live_followup.sql:41` and `:91` replace the same functions hardened in `20260627114814_catalog_provenance_write_hardening.sql:28` and `:99`. The July definitions retain identity/aggregate checks but omit media/menu approval, rights-status and verification-field immutability. Trigger names remain bound to the replaced functions. A merchant authorized for its venue has a direct API avenue to alter trust fields once these versions apply. The app editor does not submit these fields, so this is a backend boundary, not an ordinary page button. Recommendation: merge legitimate trusted-role bypass with the complete provenance guard set; inspect other function replacements. Owner: database security. Close: replay all migrations in order; owner/manager cannot change any provenance flag/rights/source/reviewer field, trusted import can; live function-definition/policy read-back. Root notified for independent review.

### P2 — substantial usability, functional or reliability gaps

**MER-04 — OCR workflow lacks both upload action and an authenticated database path.** Class: confirmed source wiring/SQL contract defects; gated-beta. `MerchantMenuScreen.tsx:408` labels navigation to `OCRDrafts` as “Use Camera”; `OCRDraftScreen.tsx:141` only adds manually/refreshes. No capture/picker/ingest occurs there. Supabase `getOCRDrafts`/accept/reject (`:5332`, `:5360`, `:5391`) access `dishes_draft` directly. Complete migration search located only the service-role ALL policy (`0013_security_hardening.sql:111`), with RLS enabled. On that schema an ordinary merchant reads no drafts or gets an authorization failure. Recommendation: real capture/upload/ingest journey and scoped authorized draft RPC, keeping ops-only authority distinct. Owner: mobile + OCR/backend. Close: signed-in merchant scans one menu, sees only own pending rows, corrects and accepts; other tenant/anonymous denied. Deployed out-of-band policies have not been inspected.

**MER-06 — Business profile save silently drops whole editable sections.** Class: confirmed source persistence defect. `BusinessProfileEditorScreen.tsx:260`; Supabase service `:5099`–`:5181`, `:1998`. UI sends cuisines/gallery/dietary/taste arrays, but live update builds no payload for them and `toMerchantOutlet` reconstructs those arrays as `[]`. “Profile updated successfully” is therefore not proof those fields saved. Recommendation: implement schema/service/read round trip or remove unsupported editable inputs until supported. Owner: backend/domain + mobile. Close: save/reopen every exposed field and public-side read-back under live adapter.

**MER-07 — “Remove” business photos does not clear saved photos.** Class: confirmed source defect. `BusinessProfileEditorScreen.tsx:185`, `:269`. UI clears form value, but conditional spread omits empty URLs; service supports clearing only if a value is explicitly passed. Original gallery is also retained in the outgoing collection. Recommendation: explicit null/empty removal contract plus gallery/reference cleanup policy. Owner: mobile/service. Close: remove profile/cover independently, save/reopen, check merchant and public display, verify previously shared assets follow the intended retention policy.

**MER-08 — Taste-tag suggestion overwrites the ingredient list.** Class: confirmed source data loss/model mismatch. `DishEditorScreen.tsx:98`, `:134`, `:183`. “Ingredients” is loaded from and saved into `tasteTags`; “Suggest taste tags” calls `setIngredients`. Merchant-written ingredients become sensory adjectives, and the later ingredient checker consumes them. Recommendation: separate typed ingredient and taste-tag fields; show a proposed diff and require apply/replace intent. Owner: mobile/domain. Close: changing suggestions never overwrites ingredient entries and each field round-trips to the proper domain property.

**MER-09 — Ingredient checker returns a reassuring result from a three-keyword stub.** Class: confirmed source behavior + safety-related UX critique. `DishEditorScreen.tsx:198`; Supabase service `:5942`. Checker tests only substrings egg/soy/noodle; for example `peanuts` produces an empty result and the UI says “No common allergens detected”. It is not a comprehensive ingredient/safety analysis, yet dietary exclusion labels are immediately customer-facing. Recommendation: remove the safety inference, identify limited suggestion coverage, retain explicit merchant confirmation/provenance and separate dietary evidence. Owner: food-data product + service/mobile. Close: known ingredient cases including nuts, dairy, seafood and mixed sauces cannot produce a misleading all-clear; no unsupported exclusion is automatically applied. This audit provides no dietary or medical advice and makes no legal compliance determination.

**MER-10 — Home verification can submit an incomplete evidence set and then fail silently.** Class: confirmed source flow defect. `HomeBasedVerificationScreen.tsx:44`, `:118`, `:130`, `:264`. Copy requires two food photos plus one menu photo, but validity requires merely `photoUris.length > 0`. Profile is saved first and each image independently promotes verification to submitted. If image two fails, image one may be submitted and the UI only logs to console; no partial-result/retry guidance. Safety acknowledgement is a local Boolean, not included in evidence payload. Recommendation: typed evidence checklist, explicit declaration record/version, upload draft batch then commit once, retain successful attachments for retry, show readable failure. Owner: mobile + verification backend/ops. Close: 1/2/3 attachments, second-upload failure, declaration persistence, cancellation and retry without duplicates.

**MER-11 — Verification lacks actionable review feedback and refresh.** Class: confirmed source UX/state gap. `VerificationCentreScreen.tsx:169`/`:181` and status switch `:127`; `HomeBasedVerificationScreen.tsx:193`. Rejection displays generic copy instead of available `rejectionReason`; `more_info_needed` falls into generic initial verification, and no status refresh action/polling exists in the screen. Home flow also offers Exact although the main profile validator rejects home-based exact when both fields are supplied. Recommendation: status-specific next step, reason/evidence checklist/history, explicit refresh or bounded foreground refresh, consistent privacy choices. Owner: merchant mobile + ops. Close: every domain verification state and server transition maps to an accurate accessible action without restarting or leaking residential data.

**MER-12 — Customer preview may open another merchant in the same building.** Class: confirmed source fallback defect. `BusinessProfileEditorScreen.tsx:308`; `MerchantMenuScreen.tsx:136`. Without signature dishes/menu venue, fallback selects `listVenuesByBuilding(...)[0]`. In a hawker centre this can be a different stall. Recommendation: expose the authoritative linked venue ID; an unlinked outlet gets an explicit unavailable/link-recovery state. Owner: domain/service + mobile. Close: empty-menu outlet in multi-stall building never previews a neighbour.

**MER-13 — Long editors have no unsaved-work protection.** Class: confirmed source omission + reasoned recovery critique. `BusinessProfileEditorScreen.tsx:193`; `DishEditorScreen.tsx:74`; `PromotionBuilderScreen.tsx:45`; `HomeBasedVerificationScreen.tsx:38`. Drafts live in component/form state; no navigation removal guard or draft persistence exists in these screens. Back, mode change, account refresh/hydration or component remount can discard entered work. Business hydration effect resets every field when outlet object changes, even during an edit. Recommendation: dirty tracking and discard confirmation; keep recoverable outlet/user-scoped drafts for lengthy media/forms, with logout cleanup. Owner: mobile. Close: back gesture, tab/outlet switch, session refresh and app interruption retain work or require explicit discard; no cross-account draft leakage.

**MER-14 — Requests are not scoped against late results; menu also relies only on future focus.** Class: confirmed source race exposure; timing-dependent runtime impact. `MerchantAnalyticsScreen.tsx:48`; `CustomerInboxScreen.tsx:48`; `MerchantDashboardScreen.tsx:253`; `PromotionBuilderScreen.tsx:65`; `MerchantMenuScreen.tsx:84`. None uses request generation/cancel checks keyed by outlet/filter/range. Slow outlet A or old filter can overwrite outlet B/current filter. Menu registers a focus listener but does not immediately load on mount/dependency change; an outlet switch while mounted need not produce a focus event. Recommendation: key cached state/requests by outlet+range/filter, drop stale responses and load on active scope plus focus; clear stale data when context changes. Owner: mobile/data-fetching. Close: delayed A request resolves after B, filter toggles rapidly, focused menu changes outlet; displayed/action targets always match active scope. No cross-tenant server authorization bypass is inferred.

**MER-15 — Dish save replaces data it did not expose for editing.** Class: confirmed source destructive update. `DishEditorScreen.tsx:133`/`:138`. Existing galleries load only the first URL but save as a one-element array; availability saves only sold_out and featured, dropping other flags. Other gallery media/availability semantics are silently removed on a routine text edit (once MER-01 is fixed). Recommendation: preserve untouched fields/unknown supported flags or implement explicit gallery/availability editors. Owner: mobile/service. Close: dish containing multiple images and additional flags retains them after price-only update; intentional removal is explicit.

**MER-16 — “View original” exposes an internal source ID instead of opening context.** Class: confirmed source unfinished behavior. `CustomerInboxScreen.tsx:75`. Button only alerts `Source ID: ...`, so merchant cannot inspect the original review/post before replying/reporting. Live adapter also maps only reviews (`supabaseService.ts:5406`) while UI offers comments and mentions; those tabs can appear as misleading empty results. Recommendation: typed source deep link with source-deleted handling; hide unsupported interaction categories or implement them. Owner: mobile/social service. Close: original action opens correct user-visible context, deleted/private sources are bounded, each advertised filter has truthful data/support state.

**MER-17 — Reply/preference operations need recovery and lifecycle hardening.** Class: confirmed source omission with runtime concerns. `CustomerInboxScreen.tsx:404` presents the reply as an absolute positioned View inside the scrolling `Screen`, not a modal/portal; backdrop/close can discard text while sending, and no keyboard avoidance/focus-isolation contract is visible. `MerchantSettingsScreen.tsx:90` starts a promise chain without catch, so background sync rejection bypasses its surrounding synchronous try/catch. Preference `:133` optimistically submits whole snapshots with no per-key serialization, allowing fast competing writes/rollback to lose a newer toggle. Recommendation: shared accessible keyboard-aware composer with draft handling; catch background failures; serialize/merge preference updates. Owner: mobile. Close: send error/close/reopen preserves draft, modal traps/restores focus with keyboard visible, rejected sync is handled, out-of-order toggles keep latest intent.

**MER-18 — AI assistant promises opportunities but live adapter returns only a summary.** Class: confirmed capability/copy mismatch; gated-beta product issue. `AIAssistantScreen.tsx:46`, `:133`; Supabase service `:5970`. Live `getAIInsights` returns only `weekly_summary`, screen filters it out, and `getWeeklySummary` repeats the same analytics request. Menu/photo/demand/promotion opportunities described on screen are therefore never actionable in this adapter. “All set” suggests completion rather than unsupported capability. Dismissal is only in local state and returns on refresh for supported providers. Recommendation: truthful summary-only product until insights exist, separate unavailable from no-action-needed, dedupe request and persist dismiss only where promised. Owner: merchant product/service. Close: live adapter fixtures for unsupported/no-data/actionable/dismissed states and one bounded analytics request.

**MER-19 — Custom controls omit important accessibility roles/states.** Class: confirmed source semantics gap; full accessibility acceptance unverified. `MerchantDashboardScreen.tsx:69` date pills omit role/selected state; `VerificationCentreScreen.tsx:275` method card omits button role/label; `HomeBasedVerificationScreen.tsx:350` privacy choices omit radio/checked state; its safety control `:304` is an IconButton with no checkbox checked state. Analytics repeated “See More” controls lack distinct accessible context. Shared Input does supply visible-label/placeholder naming and error live region, and shared IconButton adds role/name/hitSlop; these should be kept. Recommendation: semantic radio/checkbox/tab/button primitives with labels and checked/selected/disabled states; avoid duplicated generic names. Owner: mobile/accessibility. Close: VoiceOver/TalkBack announces purpose+state and sensible focus order on all 16 pages; largest supported text sizes, touch targets and measured contrast pass. No visual contrast ratio was measured in this source-only review.

**MER-20 — Price input silently turns invalid/blank values into free dishes.** Class: confirmed source validation weakness. `DishEditorScreen.tsx:125`. `parseFloat(price) || 0` accepts prefixes such as `5abc` as 5 and empty/non-numeric values as 0; name is the only required validation in handler. Recommendation: explicit SGD amount semantics, valid complete decimal parse, nonnegative bounded value and clear free-item intent; share client/service validation. Owner: mobile/domain/backend. Close: blank, pasted malformed, negative, huge and valid cents values get consistent actionable results; no accidental zero-price publication. Database constraints may reject some cases but do not repair the UI's coercion.

**MER-21 — Featured visitor operations can race across rows.** Class: source-supported race concern. `FeaturedVisitorsScreen.tsx:52`, `:89`, `:213`. Busy state is one ID and only disables that row; other reorder/pin operations can proceed against stale arrays. Earlier failure rollback can overwrite a later successful reorder; six-cap local count can race. Recommendation: serialize outlet-level changes or use revisioned server transaction and scoped optimistic cache; enforce cap on server. Owner: mobile/backend. Close: overlapping moves/pins plus one failure preserve final confirmed server order and never exceed six. Existing optimistic rollback on a single operation is a strength; no live capacity bypass was demonstrated.

**MER-23 — Menu mutations can fail with no merchant-visible error.** Class: confirmed source feedback gap. `MerchantMenuScreen.tsx:158`, `:180`, `:193`. Sold-out, featured and delete catches only console log. A busy owner cannot tell whether the menu changed; feature success does not update/reload local menu. Recommendation: per-dish pending state, explicit resulting state returned from service, visible error/retry, reconcile on focus. Owner: mobile. Close: each mutation denied/offline/slow→success, repeated tap, and consumer read-back; no false confirmation or stale availability.

**MER-24 — Team/summary messaging claims delivery before delivery evidence.** Class: confirmed source status mismatch; external delivery proof missing. `MerchantSettingsScreen.tsx:220`/`:241`; Supabase service `:6057`–`:6085`. Invite creates a pending role, writes a notification marked sent and enqueues an outbox email, then UI says “Invite sent”; weekly UI says every active team member notified. Enqueue success is not recipient delivery, acceptance or worker execution. Live worker/configuration/delivery receipts were not inspected. Recommendation: distinguish queued, sent/delivered, failed and accepted; do not block truthful account management on unavailable worker, expose retries. Owner: backend delivery + mobile. Close: controlled staging recipient, worker failure and retry, status read-back, role acceptance/revocation. Audit performed no sends.

**MER-26 — Promotion dates are converted to UTC days while the product is Singapore-local.** Class: confirmed source time-boundary mismatch. `PromotionBuilderScreen.tsx:50`, `:159`, `:169`. Date fields promise calendar dates but append `T00:00:00Z` and `T23:59:59Z`; in Singapore an offer for one date starts at 08:00 and ends at 07:59:59 the following local day. Defaults also use UTC date; editing an existing time-qualified promotion discards its original time/zone with `split("T")[0]`. Recommendation: explicitly model Asia/Singapore day boundaries or display/select timezone+times consistently; label future publish as scheduled. Owner: mobile/domain/backend. Close: tests at Singapore 00:01/07:59/08:00/23:59, existing offset timestamps, scheduled/expired transitions and customer eligibility read-back.

**MER-27 — OCR batch completion always reports success after individual failures.** Class: confirmed source outcome defect. `OCRDraftScreen.tsx:75`/`:106`. Each `handleAccept` catches errors internally, so loop continues and unconditionally alerts all drafts added; no per-row/in-flight disabling exists. Service accept is multi-step dish insert then draft update (`supabaseService.ts:5377`/`:5384`), allowing a partial commit to leave a pending draft whose deterministic dish ID then collides on retry. Recommendation: structured per-item results, progress/summary of accepted versus failed, idempotent transactional acceptance, lock pending rows. Owner: mobile + backend. Close: partial batch failure and draft-update failure with retry create no duplicate/conflicting dish and no false all-success message.

### P3 — optional polish and honest presentation

**MER-22 — Zero analytics and trends can imply activity that does not exist.** Class: confirmed presentation defects. `MerchantAnalyticsScreen.tsx:259` gives each zero segment flex 1, so zero total traffic renders a complete four-color bar despite 0% legends; `:477` formats midnight as `0 AM`. Dashboard `MerchantDashboardScreen.tsx:134` always paints an up-trend icon and green subtext without actual comparison direction. Overall judgment: promising merchant information architecture, below a dependable working beta.
