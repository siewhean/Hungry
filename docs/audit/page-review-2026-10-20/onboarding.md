Scope: all **11/11 TSX files** in the `onboarding` manifest group, plus the directly relevant stores, auth merge, recommendation repository/service, image registry and quiz-response SQL. ## Findings, ordered by severity

### ONB-01 — P1 — Confirmed source defect: completing dietary step overwrites quiz answers with neutral taste

**Evidence:** `TasteQuizScreen.tsx:146` initializes `values` from constant `INITIAL` (all axes 5). Taste-question changes write their answers to the profile at lines 272–278/523–529. The normal onboarding final Next navigates to **another route instance**, `DietaryPreferences`, at lines 692–695; both routes mount `TasteQuizScreen` (`OnboardingStack.tsx:22–23`). That new instance again initializes `values` to neutral, and dietary Continue invokes `handleFinish`, whose first instruction writes those values at line 227.

**Trigger/consequence:** choose distinctive non-neutral answers, advance to dietary and finish. The result is ranked from a neutral vector and quiz history records neutral answers, despite the user's work. The separate profile-edit flow uses an in-component phase, so it does not have this exact remount trigger; its reset/cancel issues are ONB-03/06.

**Recommendation/owner:** mobile state/navigation engineer: use one persisted draft or pass a validated answer snapshot to the dietary route; initialize edit mode from the current profile; commit one complete answer set. **Close with:** a behavior-level navigation test and device trace showing all six non-neutral values survive TasteQuiz → DietaryPreferences → result → app restart, for guest and authenticated users. Include dietary-back/forward and repeated entry. Regex presence tests cannot close this.

### ONB-02 — P1 — Confirmed source defect: fallback breaks selected dietary constraints

**Evidence:** `TasteProfileResultScreen.tsx:22–30` constructs dietary-filtered criteria. Lines 43–47 replace zero ranked matches with unfiltered `repository.listPopularNearby()`. Lines 55–58 repeat that fallback for server results. Both mock and Supabase repository popular methods lack a dietary argument (`mock/repositories.ts:78–79`, `supabaseRepository.ts:1073–1077`). Non-empty results are then described as “aligned with your current preferences” at line 82.

**Trigger/consequence:** select restrictions whose conjunction has no catalog match. Popular dishes with different/unknown flags can be shown as suitable preferences. This is a hard-filter contract failure; no claim that dietary tags establish allergy safety or certification is made.

**Recommendation/owner:** recommendation/data engineer + consumer product owner: retain all hard restrictions through every fallback, and use an honest empty state with explicit user-controlled relaxation only for soft preferences. Avoid implying unknown dietary evidence is verified. **Close with:** mock and Supabase behavior tests for zero matches, unknown flags and multiple restrictions; every displayed dish must satisfy selected hard flags or the view must remain empty. Inspect actual backend tag evidence before making certification claims.

### ONB-03 — P2 — Confirmed source defect: back navigation visually changes the selected answer without changing its value

**Evidence:** `TasteQuizScreen.tsx:176–187` recenters every question at `SNAP_INTERVAL`; `animateStep` also sets `snappedIndex(1)` at line 205. Rendering marks the card selected using that index at line 534. Previously saved `values[currentKey]` is independent and retained. A backward question therefore displays Balanced/Medium even when the retained answer is 2 or 8; no Next handler reconciles the selection from the current answer.

**Trigger/consequence:** choose Fiery, advance, press Back. Screen and accessibility selected state can say Medium while the model keeps Fiery. The user cannot trust corrections. **Recommendation/owner:** mobile interaction engineer: derive selected index and initial/revisit offset from each question's draft value. **Close with:** forward/back test for all three choices, rotation, and VoiceOver/TalkBack selected state; verify UI and submitted snapshot agree.

### ONB-04 — P2 — Confirmed product/data mismatch: mandatory cuisine selections are discarded unless optional dishes are also selected

**Evidence:** `CuisineSelectionScreen.tsx:214–215` keeps cuisine/dish selection locally. `handleNext` at 252–259 persists only visible selected dish IDs. The primary CTA is disabled without at least one cuisine at line 391; there is no skip or “all cuisines” action. No cuisine IDs are passed onward. `onboardingSelectedDishIds` does affect Home ranking (`features/home/feed.ts:88`), so optional dish inputs have a real downstream use, but cuisine-only inputs do not.

**Trigger/consequence:** select Japanese, select no optional dish, finish. Mandatory effort produces no lasting preference; users who want all cuisines or do not know these categories must select something to reach the quiz's later Skip. **Recommendation/owner:** onboarding product/UX + recommendation engineer: either persist/use a cuisine preference with transparent meaning, or make this an optional examples step; provide a direct browse/skip choice. Avoid treating “Muslim-friendly” as a cuisine or a certification merely because it shares the grid. **Close with:** inspect stored preference and changed ranking for cuisine-only input; prove no-preference users can proceed without inventing a choice.

### ONB-05 — P2 — Runtime concern backed by source: core onboarding has no robust small-screen, keyboard or restart-draft treatment

**Evidence:** `WelcomeScreen.tsx:17,61–68,74,123,195–233` uses initial window height, a non-scroll root, large fixed margins and a footer; `OnboardingAuthScreen.tsx:190–200,289–460` uses non-scroll Views with no keyboard-avoidance wrapper. `LocationPermissionScreen.tsx:112–219` contains illustration, three min-height cards and footer in a non-scroll root. Cuisine/quiz current question and selections are local state (`CuisineSelectionScreen.tsx:214–215`, `TasteQuizScreen.tsx:146–155`), while only profile/location/session state is persisted. Theme font scaling caps exist; they do not establish usable reflow.

**Trigger/consequence:** small viewport, open keyboard or process death during setup. Controls may be obscured and route/question/cuisine draft cannot be restored faithfully. Exact clipping is **not observed** in this review. Quiz answers partially persist on selection, but remount starts neutral and step 0; dietary/budget changes persist only on Finish.

**Recommendation/owner:** mobile UX/accessibility engineer: use measured scrollable content with stable bottom actions and keyboard handling; store a versioned, non-secret onboarding draft and resume route. Do not persist passwords. **Close with:** smallest supported iPhone/Android, keyboard open on every auth field/manual search, maximum supported font setting, rotation and kill/relaunch mid-step. Show controls remain reachable and non-secret draft survives.

### ONB-06 — P2 — Confirmed source defect: answer browsing commits immediately and records repeated completed-quiz signals

**Evidence:** `TasteQuizScreen.tsx:272–278,523–529` invokes `setTasteVector` for individual taps/swipe settlement; profile mode initializes neutral values at line 146. `useProfileStore.ts:564–590` records `taste_quiz_completed`, appends a completed quiz event, and increases recommendation signal count/confidence for each invocation; authenticated users also issue an async backend update at 597–603. `Skip` in profile mode only navigates back (`TasteQuizScreen.tsx:724–726`).

**Trigger/consequence:** begin editing a known profile, change one axis or browse multiple cards, then leave. Existing axes can be replaced by neutral draft defaults, edits are already committed, and one unfinished quiz becomes multiple “completed” signals. Concurrent remote writes have no per-edit revision ordering here; out-of-order server persistence is an additional runtime risk, not observed evidence.

**Recommendation/owner:** recommendation instrumentation + profile-state engineer: separate draft changes from explicit commit, record one quiz completion event with honest answered/default provenance, and define cancellation semantics. **Close with:** open/cancel causes zero profile writes/completion signals; one completed quiz causes one event and consistent persisted vector; rapid interactions with delayed writes retain the final revision.

### ONB-07 — P2 — Confirmed source defect: signing in to save loses the original Save action

**Evidence:** result heart for a guest shows a warning and navigates to `OnboardingAuth` without a dish/intent parameter (`TasteProfileResultScreen.tsx:131–140`). `OnboardingAuthScreen.tsx:72–74` always continues to LocationPermission after successful authentication. No queued save/return to the result exists in that path.

**Trigger/consequence:** guest taps Save, creates/signs in successfully and finishes location. The intended dish is still unsaved and the result page is gone. Auth is a multi-step interruption with no payoff for the action that caused it. **Recommendation/owner:** auth/navigation + favourites engineer: retain the concrete save intent, execute it once after verified authentication, and restore the result context or show success with the saved dish. **Close with:** guest Save → email/password or verification → location → saved-dish read-back; cancellation must not save, repeated callbacks must not toggle it back off.

### ONB-08 — P2 — Confirmed source defect: real recommendation images can depict unrelated food

**Evidence:** result uses `getOnboardingDishImageSource(dish.id)` and labels it `Photo of ${dish.name}` (`TasteProfileResultScreen.tsx:102–106`). Registry `onboardingFoodImages.ts:227–245` maps only a small mock-style ID list; all unknown real IDs return chicken rice. Even explicit mappings use ramen for salmon don/sushi and fish soup for ban mian. The inspected asset contract requires this generated local mapping, so merely passing that contract cannot establish truthful image identity.

**Trigger/consequence:** a Supabase catalog result uses an ID absent from the map or a mismapped known dish. A different dish image is presented as its photo, damaging the dish-first decision. **Recommendation/owner:** catalog/UX + asset-provenance owner: match a real approved image by actual identity, or show clearly described illustration/unavailable state. Preserve licensing/provenance requirements while revising the misleading contract. **Close with:** inspect real catalog IDs, known mismaps and unknown IDs; image subject and accessible description must agree, with provenance evidence. Do not substitute unauthorised remote assets.

### ONB-09 — P2 — Confirmed source gap: auth/preview async operations do not expose reliable progress and recovery

**Evidence:** `OnboardingAuthScreen.tsx:89–185` starts remote operations, while submit buttons at 385–389 and 451–455 have no `loading`, `disabled` or submission guard. The provider handler likewise has no pending guard when that feature is enabled. `TasteProfileResultScreen.tsx:50–66` has no loading/error/retry state and swallows failures; empty and failed catalog reads use the same vague message at 81–84. Result data is fetched once, so returning after changed preferences also requires stale-result verification.

**Trigger/consequence:** slow sign-up/sign-in or catalog failure. Users can duplicate requests and cannot distinguish a temporary fetch failure from no suitable dishes. Repeated email submits can create confusing server/rate-limit responses. **Recommendation/owner:** mobile auth + discovery engineers: wire `isSubmitting`/explicit pending state, disable duplicate submission, preserve form values and give contextual retry; use loaded/error/empty states without blocking Continue unnecessarily. **Close with:** delayed/rejected requests, double taps, retry and offline-to-online test; exactly one auth operation per pending intent, clear recovery and retained inputs.

### ONB-10 — P2 — Reasoned race risk: manual location can be overwritten by an older GPS request

**Evidence:** Location Continue awaits `grantLocation` (`LocationPermissionScreen.tsx:83–109`); manual-entry action remains enabled at 213–216 during that pending request. Manual picker commits manual coordinate and completion at `ManualLocationPickerScreen.tsx:117–121`. A late GPS result in `useLocationStore.ts:112–124` unconditionally writes live coordinates and clears manual fields; its caller then runs `finish()`.

**Trigger/consequence:** slow GPS, enter manual picker, select area before the older GPS result resolves. The manual choice can be replaced and navigation/completion can fire again. Timing not reproduced on a device here. **Recommendation/owner:** location-state engineer: use a request generation/cancellation guard or invalidate pending GPS work when choosing manual mode; ensure completion is idempotent. **Close with:** controlled delayed location promise resolved after manual submit; location remains the selected area and only one completion/navigation occurs.

### ONB-11 — P2 — Confirmed accessibility gap: onboarding animations bypass the existing reduced-motion preference

**Evidence:** Welcome entrance sequence (`WelcomeScreen.tsx:35–46`), cuisine stagger/press animation (`CuisineSelectionScreen.tsx:102–106,231–237`), auth transitions (`OnboardingAuthScreen.tsx:49–61`), intro template animations and quiz lateral transitions (`TasteQuizScreen.tsx:189–223`) run without `useReduceMotion`. The existing hook explicitly combines app and OS preferences (`src/hooks/useReduceMotion.ts:6–31`), while theme returns static motion tokens. Onboarding does include useful labels/checkbox states, so this is a specific omission rather than an absence of accessibility work.

**Trigger/consequence:** OS/app Reduce Motion enabled; large lateral slides, staggered entrances and spring effects still run. **Recommendation/owner:** accessibility/mobile interaction engineer: use the shared hook to render the stable state directly or use minimal fades; do not leave content initially invisible in the reduced path. **Close with:** iOS and Android preference enabled before launch and toggled while mounted; all content/actions remain available without travel animation.

### ONB-14 — P2 — Confirmed source transition defect: verification completes onboarding before location

**Evidence:** `OnboardingAuthScreen.tsx:99–111` resets to EmailVerification with `completedOnboarding: true` when sign-up returns no session, even though its own finish helper says location is still required (70–74). `EmailVerificationScreen.tsx:107–114` applies that flag and calls `completeOnboarding()`. `RootNavigator.tsx:597–603` then navigates Home. Existing account/same-screen successful sign-up instead goes to location.

**Trigger/consequence:** Save result as guest → sign-up with email confirmation required → verify. User bypasses location and can reach Home with the default/stale location; skipped-quiz flag is also reset to the default false by `completeOnboarding()` in verification. **Recommendation/owner:** auth/navigation engineer: carry a precise resume step and actual existing onboarding completion state, then return to location for unfinished users. **Close with:** email-confirmation enabled/disabled, guest who previously completed onboarding, expired-code retry and app-restart/deep-link verification scenarios; finish location exactly when required and preserve the quiz skip state.

### ONB-12 — P3 — Reasoned UX critique: preview does not explain or enable acting on the recommendation

**Evidence:** `TasteProfileResultScreen.tsx:95–155` displays image/name/two taste tags/heart, without price, venue, explanation of fit or dish-detail navigation. `getResultFilters` omits the just-requested budget (22–30), and `useProfileStore.ts:678–680` stores budget locally. “Usual budget” might intentionally be a soft signal elsewhere; this preview does not apply or describe it.

**Consequence/recommendation:** a hungry user cannot judge “can I afford it / where is it / why this?” before being sent through location. Product/recommendation owner should show a compact useful preview, respect or explicitly describe budget scope, and make details discoverable. Avoid pretending nearby relevance before location setup. **Close with:** budget-bound result scenarios and a usability check where a participant explains the recommendation and finds its price/venue without guessing. Optional polish only after P1 defects.

### ONB-13 — P3 — Confirmed copy/semantics mismatch: location Continue hides the OS-permission action and Back describes the wrong screen

**Evidence:** `LocationPermissionScreen.tsx:199–203` labels the permission request “Continue”, while approved Stitch brief calls for allow-location wording. When no manual location exists, this button triggers OS foreground permission. Its back label says “Back to taste quiz” (131) but ordinary flow arrived from TasteProfileResult and `goBack()` returns there (133–138); skipped flow differs again. Native back controls are 40×40 (143–145), below the shared `componentSizes.touchTarget` of 44; result heart target also deserves actual hit-area measurement.

**Recommendation/owner:** onboarding UX/accessibility owner: say “Use my location” before permission and “Continue” for a selected manual area; use destination-correct Back semantics and token touch targets. Keep equal access to manual selection. **Close with:** inspect permission action name and focus output on completed/skipped/manual routes; verify effective native targets, not just icon dimensions. No store-policy violation is asserted solely from this copy.

## Priorities and readiness boundary

1. Mobile/recommendation engineers: close ONB-01 and ONB-02 with behavioral tests and artifact evidence before describing the taste onboarding as production-ready.
2. Mobile/auth engineers: fix answer/selection consistency and commit semantics (ONB-03/06), resume the concrete Save intent (ONB-07), and correct verification's unfinished-onboarding flag (ONB-14).

5. Product owner: then refine budget/explanation/context and permission/back wording (ONB-12/13), with approved current design artifacts and a short real-user task review.
