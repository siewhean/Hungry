## Findings

### PROFILE-01 — P1 — Follow action is incompatible with the checked-in permission contract

**Class:** confirmed source/API-to-SQL mismatch; production reachable. **Locations:** `src/lib/services/supabase/supabaseService.ts:3923` / `:3930`; `supabase/migrations/0023_integration_posts_privacy_chat.sql:367`; callers `ProfileConnectionsScreen.tsx:395`, `UserProfileContent.tsx:322`; rollback `src/store/useSocialStore.ts:299`.

**Trigger / consequence:** signed-in user presses Follow on another UUID. Client upserts `status: "approved"`; the sole checked-in follow insert policy requires `status = 'pending'` and `approved_at is null`. An ordinary authenticated client applying these migrations cannot perform that insert. Optimistic Following briefly appears, then rolls back with a console error. There is no pending/request/cancel/approval UI here. This is failed follow functionality, **not a demonstrated privacy bypass**: SQL currently rejects the overprivileged state.

**Recommendation / owner:** social backend + profile engineer: define server-side public-account immediate follow/private-account request semantics, use that authoritative API, represent pending/approved/rejected explicitly, and surface a retryable failure. Preserve caller/target identity guards; do not fix by loosening RLS globally. **Close with:** two real test identities, public/private targets, fresh insert, retry, duplicate tap, pending approval/rejection, cancellation, block, and forbidden self-approval against migrated local/staging DB. Confirm deployed policy separately.

### PROFILE-02 — P1 — Editable email changes profile data but leaves authentication identity unchanged

**Class:** confirmed source defect; production. **Locations:** `EditProfileScreen.tsx:175`, `:203`; `supabaseService.ts:3373`, `:3401`, `:640`, `:2993`.

**Trigger / consequence:** enter a new email and save. Service only upserts `user_profiles.email`; it never requests a Supabase Auth email change. Reopening shows the new address, while sign-in/password reset still belong to the old auth email. Worse, `changePassword()` reauthenticates using `currentSession.profile.email`, resolved from that editable row, and reports “Current password is incorrect” despite a correct password. This is a concrete account-control failure after an accepted edit; no account takeover is claimed.

**Recommendation / owner:** auth + profile engineer: use a verified auth email-change flow with pending confirmation state; derive sign-in identity from the auth user; otherwise make this field read-only with precise labeling. Validate email and nonblank display name inline per governing spec (current handler sends both unvalidated). **Close with:** save different email, confirm/cancel/expire link, reopen, sign-in, reset and change-password before/after confirmation; blank/malformed/long/non-Latin display names; ensure no profile/auth split on partial failure.

### PROFILE-03 — P2 — Followers, following, and public counts do not represent the selected user's social graph

**Class:** confirmed source data-integrity defect; production. **Locations:** `ProfileConnectionsScreen.tsx:226`, `:262`, `:278`; `ProfileHomeScreen.tsx:377`, `:415`; `UserProfileContent.tsx:354`, `:360`.

**Trigger / consequence:** open Followers: the list unions real service followers with every author seen in community posts, comments, replies and chat-profile enrichment. Those authors are displayed as followers without a follow relationship. Self count uses `Math.max(real count, unrelated author count)`; following adds local flags to server counts, double-counting the same UUID. Open another user's Following: it unions that user's result with **the viewer's** followed IDs/names. Public profile shows Followers as only 0/1 depending on the viewer's local follow and Following as a constant 0. Two distinct UUIDs sharing a display name are collapsed by name dedupe.

**Recommendation / owner:** profile/social engineer: relationships must come exclusively from target-user approved edges; use UUID keys; treat local optimism as one overlay on the matching edge, and keep people suggestions separately labeled. Resolve authoritative counts consistently with the list, or hide unproven numbers. **Close with:** deterministic fixture graph A→B, C→B, A→D; unrelated poster E; B/C same display name; verify each target's counts and lists, uninstall/reinstall, unfollow and offline states.

### PROFILE-04 — P2 — Profile ownership and public “Reviews” are inferred from names and local comments

**Class:** confirmed source identity/semantics defect; production. **Locations:** `ProfileHomeScreen.tsx:303`; `UserProfileContent.tsx:229`, `:267`, `:375`; public profile fetching `:161`.

**Trigger / consequence:** two users choose the same display name. Self posts accept `authorId === profile.id OR name matches`, so another user's accessible post can appear as mine even when its UUID disagrees. Other-user Reviews are local cached comments/replies matched by display name, not that author's submitted dish reviews; in production comments are gated off, making this particularly misleading. On a public profile, Stalls navigates with `navigation.navigate("VisitedStalls")` and no author target; that screen derives the current viewer's history, and the root UserProfile navigator has no sibling VisitedStalls route. It can therefore be unhandled in the root context; it cannot produce the promised other-user stall list.

**Recommendation / owner:** profile + review engineer: UUID wins whenever present; isolate name fallback to mock data only. Use an author-scoped review API, or label actual comment activity honestly. Pass a typed target for another person's visible venues or remove the link until implemented. **Close with:** duplicate-name account fixture, changed display name, renamed/deleted author, public reviews from fresh install with no cached comments, root-route Stalls press and back behavior.

### PROFILE-05 — P2 — Untouched optional hours submit a fabricated Monday 10 AM–10 PM

**Class:** confirmed source data defect; production. **Locations:** `AddStallScreen.tsx:228`, `:490`, `:821`.

**Trigger / consequence:** add only mandatory name/photo and submit. State starts with Monday and default 10:00–22:00, and the submit formatter includes it. Copy says hours may be left blank, but the sole row cannot be removed and the last selected day cannot be deselected. The queue receives an asserted schedule the contributor never supplied. Days may appear only once, preventing common split-service schedules on one day; equal start/end silently drops the row instead of explaining 24-hour/invalid intent.

**Recommendation / owner:** contribution engineer + product: start with no claimed hours or an explicit Unknown state; add hours deliberately, allow remove-last, represent overnight/24-hour and split periods explicitly. **Close with:** untouched optional hours → null; remove-last; lunch+dinner on same day; overnight; 24-hour; one invalid row; holiday uncertainty; inspect serialized RPC payload.

### PROFILE-06 — P2 — Long edit/contribution drafts vanish on navigation without a discard boundary

**Class:** confirmed state-lifetime behavior plus UX critique; production. **Locations:** `AddStallScreen.tsx:216–254`; `EditProfileScreen.tsx:40–43`, `:100`; shared back path `ProfileScreenShell.tsx:25`.

**Trigger / consequence:** enter photos, address, several menu rows/hours, then pop/unmount the editor through accidental back/swipe, reset the root route, or restart the app. Ordinary pushed quiz/password routes can keep the editor mounted and do not by themselves prove loss (independent cross-check correction). Draft exists only in component state; no before-remove guard or persisted draft was found. Avatar picker reports “Profile photo updated” before the save succeeds, encouraging a user to leave and lose it. Recoverable submit failures keep the in-session form, which is good; navigation/restart does not.

**Recommendation / owner:** profile/contribution engineer: establish dirty state, accessible discard/save-draft choices, and optional account-scoped resumable submission drafts; say “Photo selected” until saved. Preserve form through auth expiry and upload retry. **Close with:** iOS swipe, Android back, header back, background/relaunch, failed save, subsequent retry, quiz/password return. This is bounded form work; do not require persistent drafts for every small preference control.

### PROFILE-07 — P2 — Saved/tried/visited/followed screens discard IDs not already in the synchronous cache

**Class:** confirmed missing resolution/recovery path; production; frequency requires runtime proof. **Locations:** `FavouritesScreen.tsx:23–25`, `:35`; `VisitedStallsScreen.tsx:35–40`; `FollowedStallsScreen.tsx:27–29`; `ReviewHistoryScreen.tsx:35`; `supabaseRepository.ts:1058–1066`; `useProfileStore.ts:381–407`.

**Trigger / consequence:** remote saved/followed IDs are present but their dish/venue records are absent from a cold/partial cache, or favourite-ID rehydration fails. Synchronous `get*ById` + filter drops them, leaving nonzero counts beside empty/partial content. Cache hydration mutates module arrays asynchronously without a page subscription; these screens have no targeted fetch or cache-ready update. The profile store exposes `favouritesRehydrationFailed`, but Favourites never consumes it. ReviewHistory retains review text on missing dish, but falls back to generic “Reviewed dish” instead of resolving the missing item.

**Recommendation / owner:** profile + catalog engineer: batch-resolve saved IDs through a scoped repository query; expose loading, unavailable/deleted records, stale/offline data, and retry instead of treating unresolved as absent. Support the catalog V2 identity path explicitly. **Close with:** cold cache + saved IDs outside first page, cache completion after mount, failed ID fetch, removed item, offline reopen, refresh; totals must reconcile or explain inaccessible entries. No claim that saved backend records were actually deleted.

### PROFILE-08 — P2 — Several profile reads conflate failure, missing data and empty results

**Class:** confirmed missing failure distinctions/retry paths; production except SocialGrid. Independent cross-check confirms Connections and SocialGrid do render initial spinners; do not generalize absent loading feedback to those screens. **Locations:** `FollowedStallsScreen.tsx:24`; `ReviewHistoryScreen.tsx:25`, `:121–128`; `UserProfileContent.tsx:161–186`; `ProfileConnectionsScreen.tsx:110`; `ProfileHomeScreen.tsx:264`, `:303`; `SocialGridScreen.tsx:64`.

**Trigger / consequence:** network/auth failure, initial load, or private content denied by RLS. FollowedStalls silently catches and says nobody followed; ReviewHistory initially says “No reviews yet” while loading and its failure state has no retry action; other profile has no loading/private/blocked/not-found/error distinction and author service failure is caught into `[]`. Shared-post helper also swallows upstream errors. Returning to the still-mounted history page after posting does not refetch because the effect depends only on profile ID/provider. ProfileHome fires `loadStallSubmissions()` without catch, creating an unhandled rejection on failure. SocialGrid logs failure and renders empty content.

**Recommendation / owner:** profile engineer: a small explicit loading/empty/error/forbidden/stale state model, focus refresh and accessible Retry; preserve last known content with stale labeling. Do not infer private/public state solely from zero posts. **Close with:** delayed response, airplane mode, expired session, 403 private target, deleted UUID, successful retry and return from review creation; assert no unhandled promise rejection. Some services already convert query errors to `[]`, so propagate typed errors through that layer too.

### PROFILE-11 — P2 — Passport celebration cancels its own completion timer

**Class:** confirmed React effect lifecycle defect by source reasoning; **gamification-gated beta only**. **Locations:** `PassportScreen.tsx:121–141`.

**Trigger / consequence:** first uncelebrated stamp. Effect calls `setCelebratingStampId(id)` and starts a timeout intended to mark it celebrated. That state is an effect dependency; the rerender cleans up the previous timeout. The next effect returns because the celebrating ID equals the marker, so it never calls `markStampCelebrated` or clears celebration. Announcements/replay persistence may repeat on later mounts; animation can remain in celebrating state. Source regex test merely checks that the intended calls exist.

**Recommendation / owner:** gamification engineer: give timer ownership to a separate effect keyed by celebrating ID, or use a ref/state transition that cannot immediately cancel completion. **Close with:** fake-timer component test for 300/1,400 ms, reduced motion, unmount/remount, second earned stamp, Strict Mode; inspect actual one-time announcement. Keep production gate until behavior passes.

### PROFILE-12 — P2 — Weekly missions and passport loads lack freshness and failure feedback

## Explicit states and edge cases

- **Identity:** own/other, missing UUID, stale route name/avatar, same-name users, renamed account, private/unfollowed/pending/approved/blocked/deleted user; current code conflates several. UUID-auth enforcement and private queue boundaries are strengths; public presentation is not yet consistent.
- **Reads:** first load, empty, service fail, slow request, offline cache, record deleted/hidden, cache completes after screen mount, reload on focus, older paginated items and 21+ submissions. Several pages only implement real-empty and fail-to-empty; this is a user-facing trust gap, not proof of data loss.
- **Writes:** duplicate tap, failure rollback, multiple parallel edits, app leaves screen midflight, auth expires, image 2/6 fails, RPC succeeds but reply/readback fails, secondary reward fails. Duplicate-submit guard and nonblocking rewards are good; canonical confirmation and draft recovery need stronger contracts.
- **Form/device:** blank and whitespace name, invalid email/URL/postcode, long/multilingual input, HEIC and limited media access, denied permanently, picker throws/cancels, keyboard covering save, six-photo reorder with assistive input, 24-hour/overnight/split hours, no known hours, Android cancel and iOS sheet swipe. Native branches were read, not executed.
- **Accessibility:** labels/states, actual hit areas, heading order, announcements, focus restoration from menu/sheets, reduce motion, haptic preference, dark/light contrast, max dynamic type and right-to-left layout. Source gives useful progress in decorative-image and self-tab semantics; full accessible usability is unverified.
- **Scale:** own post grids, follower lists and history are eager ScrollView children; nested ScrollViews appear in followed/visited/connections/passport; these are runtime risks at large account sizes. Use one scroll owner plus virtualized lists where actual unbounded history warrants it; no measured jank claim.

**Product judgment:** the strongest Hungry assets are the six-dimensional taste identity, dish-first saves, and contribution queue. The weakest production part is trust in the profile: social stats appear authoritative while their construction is synthetic or viewer-local, email edits imply an auth change they do not perform, and empty pages conceal read failures. The own profile currently spends its first screen on social counts and repeats contribution/menu access before showing the user's food memory. For the core “what should I eat?” task, test a hierarchy of saved food / reviewed food / taste preferences before follower metrics. This is an explicit UX recommendation, not a claimed design violation or request to remove social features.
