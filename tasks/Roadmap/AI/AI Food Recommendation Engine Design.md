# AI Food Recommendation Engine Design

> **Pillars covered:** Data Modeling · Recommendation Algorithm · Infrastructure & API

---

## 1. System Overview

**Mission:** Deliver a personalized dish recommendation on first app open and continuously improve it with every interaction, without requiring the user to wait for a large interaction history.

### Data Flow

```
Taste Quiz
    │
    ▼
user_taste_vectors (pgvector)
    │
    ├──► Cosine similarity query → Ranked dish candidates
    │
    ├──► Interaction events (save / rate / view / order)
    │         │
    │         ▼
    │    Weighted delta update → refined user_taste_vectors
    │
    └──► Collaborative neighbors → dishes similar users saved
                │
                ▼
         Recommendation slate (20 dishes)
                │
         Three-tier cache (Zustand → Redis → pgvector)
                │
                ▼
         React Native screens
```

### Technology Stack

| Layer | Technology | Purpose |
|-------|-----------|---------|
| Vector store | Supabase + pgvector `vector(6)` HNSW | Cosine similarity at <20ms |
| Proximity filter | PostGIS `ST_DWithin` | Reduce candidates from 100k → ~500 before vector search |
| AI tagging | Claude Haiku | Auto-generate dish taste vectors + flavor tags from text |
| Edge compute | Supabase Edge Functions (Deno) | Zero cold-start, co-located with Postgres |
| Redis cache | Upstash (TTL 5 min) | Absorb repeat queries from same location |
| Client cache | Zustand (`useDiscoveryStore`) | Zero-network for in-session repeat queries |

### Phase Roadmap

| Phase | Trigger | Engine State |
|-------|---------|-------------|
| **Phase 1** (now) | App launched | Mock cosine similarity in `mockRepository.getDecideForMe()` |
| **Phase 2** | Supabase deployed | Live pgvector cosine similarity; quiz seeds instantly |
| **Phase 3** | ≥50 active users | Hybrid: content (40%) + collaborative (40%) + social (20%) |
| **Phase 4** | ≥500 dishes | Claude Haiku auto-tagging nightly batch active |


### 2.2 Confidence Score Columns

Add to `user_taste_vectors` to track profile warmth:

```sql
ALTER TABLE user_taste_vectors
  ADD COLUMN confidence   NUMERIC(4,3) NOT NULL DEFAULT 0.0,
  ADD COLUMN signal_count INT          NOT NULL DEFAULT 0,
  ADD COLUMN last_signal  TIMESTAMPTZ;
```

| Confidence Range | Meaning |
|-----------------|---------|
| 0.0 – 0.2 | Cold start — quiz only |
| 0.2 – 0.6 | Warming — <20 interactions |
| 0.6 – 1.0 | Warm — ≥20 interactions |

### 2.3 New Tables

```sql
-- Immutable audit log of every interaction that shapes the taste profile
CREATE TABLE taste_interaction_events (
  id         BIGSERIAL PRIMARY KEY,
  user_id    UUID      NOT NULL REFERENCES users(id)  ON DELETE CASCADE,
  dish_id    UUID      NOT NULL REFERENCES dishes(id) ON DELETE CASCADE,
  action     TEXT      NOT NULL CHECK (action IN ('view','save','unsave','rate','order','dismiss','share')),
  rating     SMALLINT,           -- only when action = 'rate'
  dwell_ms   INT,                -- only when action = 'view'
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_tie_user_recent ON taste_interaction_events (user_id, created_at DESC);
CREATE INDEX idx_tie_dish        ON taste_interaction_events (dish_id, action);

-- Extended flavor tags beyond the 6 axes (generated by Claude Haiku)
CREATE TABLE dish_flavor_tags (
  dish_id    UUID         NOT NULL REFERENCES dishes(id) ON DELETE CASCADE,
  tag_slug   TEXT         NOT NULL,   -- e.g. 'charred', 'creamy', 'umami_bomb'
  confidence NUMERIC(4,3) NOT NULL DEFAULT 1.0,  -- 0–1; model confidence
  source     TEXT         NOT NULL DEFAULT 'claude', -- 'claude' | 'manual' | 'crowd'
  PRIMARY KEY (dish_id, tag_slug)
);
CREATE INDEX idx_dft_tag ON dish_flavor_tags (tag_slug, dish_id);

-- Cached recommendation slates (invalidated on profile update or >500m location shift)
CREATE TABLE recommendation_cache (
  id           BIGSERIAL PRIMARY KEY,
  user_id      UUID        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  geo_cell     TEXT        NOT NULL,  -- S2-style cell key at ~500m resolution
  payload      JSONB       NOT NULL,  -- serialized RecommendationResult[]
  generated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at   TIMESTAMPTZ NOT NULL,
  UNIQUE (user_id, geo_cell)
);
CREATE INDEX idx_rc_expiry ON recommendation_cache (expires_at);

-- Raw quiz answers preserved for future model retraining
CREATE TABLE quiz_responses (
  id          BIGSERIAL PRIMARY KEY,
  user_id     UUID        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  question_id TEXT        NOT NULL,
  option_id   TEXT        NOT NULL,
  taste_delta JSONB       NOT NULL,  -- {sweet:+1, spicy:+2, ...}
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_qr_user ON quiz_responses (user_id, created_at DESC);
```

### 2.4 Dish Tagging Taxonomy

Three tiers of tags are maintained in parallel:

| Tier | Storage | Example |
|------|---------|---------|
| Axis values | `dish_taste_vectors.vector` | `sweet=3, spicy=8` |
| Flavor descriptors | `dish_flavor_tags` | `charred`, `umami_bomb`, `fragrant_herbs` |
| Dietary flags | `dish_dietary_flags` (existing) | `vegetarian`, `halal` |

Combined filter query:

```sql
SELECT d.id, 1 - (dtv.vector <=> $user_vector) AS similarity
FROM   dishes d
JOIN   dish_taste_vectors dtv ON dtv.dish_id = d.id
JOIN   dish_dietary_flags ddf ON ddf.dish_id = d.id
                              AND ddf.flag_id = ANY($dietary_flags)
WHERE  d.venue_id IN (
  SELECT id FROM venues
  WHERE  ST_DWithin(location, ST_Point($lng, $lat)::geography, $radius_m)
)
ORDER  BY dtv.vector <=> $user_vector
LIMIT  20;
```

## 3. Recommendation Algorithm

### 3.1 Phase 1 — Cold Start via Quiz

The Taste Quiz seeds `user_taste_vectors` immediately on sign-up. First recommendations are personalized with zero interaction history.

```
user_vector = normalize(quiz_answers × taste_impact_weights)

SELECT dishes
ORDER BY dish_taste_vectors.vector <=> user_vector
WHERE  ST_DWithin(venue.location, user_location, 500m)
LIMIT  20
```

### 3.2 Phase 2 — Feedback Loop (Warm Profile)

Every user interaction triggers a weighted delta update on the taste vector:

| Signal | Vector Delta | Confidence Δ |
|--------|-------------|-------------|
| Save a dish | `+0.25 × (dish_vector − user_vector)` | +0.04 |
| Rate 5★ | `+0.20 × (dish_vector − user_vector)` | +0.03 |
| Rate 3★ | `+0.05 × (dish_vector − user_vector)` | +0.01 |
| Rate 1★ | `−0.15 × (dish_vector − user_vector)` | +0.02 |
| View > 15s | `+0.03 × (dish_vector − user_vector)` | +0.005 |
| Dismiss/skip | `−0.05 × (dish_vector − user_vector)` | +0.005 |
| Order complete | `+0.30 × (dish_vector − user_vector)` | +0.05 |

All dimension values are clamped to `[0, 10]`. Recency decay is applied before each update:

```
effective_weight = base_weight × e^(−0.05 × days_since_interaction)
```

### 3.3 Phase 3 — Collaborative Filtering

Once ≥50 active users exist, find the 10 nearest taste-profile neighbors:

```sql
-- Step 1: find neighbors
SELECT u2.user_id, 1 - (u2.vector <=> $user_vector) AS similarity
FROM   user_taste_vectors u2
WHERE  u2.user_id != $user_id
ORDER  BY u2.vector <=> $user_vector
LIMIT  10;

-- Step 2: surface dishes those neighbors saved that the current user hasn't seen
SELECT dish_id, COUNT(*) AS neighbor_saves
FROM   taste_interaction_events
WHERE  user_id   = ANY($neighbor_ids)
  AND  action    = 'save'
  AND  dish_id  NOT IN (
    SELECT dish_id FROM taste_interaction_events WHERE user_id = $user_id
  )
GROUP  BY dish_id
ORDER  BY neighbor_saves DESC
LIMIT  10;
```

Final blend weights: **content 40% · collaborative 40% · social graph 20%**

### 3.4 Diversity Post-Processing

After ranking, the top-20 slate is post-processed to prevent clustering:

- ≤3 dishes from the same venue
- ≤2 dishes sharing the same highest taste dimension
- 1 "wild card" dish with similarity 0.4–0.6 (outside the user's comfort zone)

## 4. Claude Haiku Dish Tagging Pipeline

**Purpose:** Auto-generate `dish_taste_vectors` and `dish_flavor_tags` from unstructured text (dish name, description, review excerpts) so new dishes are instantly searchable without manual tagging.

**Triggers:**
- New dish added to the catalog
- Dish accumulates 10+ new reviews since last tagging run

**Batch job** (Supabase scheduled function, nightly 2 AM SGT):

```
for each untagged/stale dish:
  prompt   = buildTaggingPrompt(dish.name, dish.description, latestReviews)
  response = await claude_haiku.complete(prompt)
  vector   = parseVector(response)   // {sweet:6, spicy:8, sour:2, salty:5, rich:7, aromatic:9}
  tags     = parseTags(response)     // ['charred', 'fragrant_herbs', 'crispy_skin']
  upsert dish_taste_vectors
  upsert dish_flavor_tags
```

**Prompt template:**

```
You are a food flavor analyst. Given this dish information, output ONLY a JSON object with:
- "vector": {sweet: 0-10, spicy: 0-10, sour: 0-10, salty: 0-10, rich: 0-10, aromatic: 0-10}
- "tags": string[] (max 6, from: charred, creamy, citrusy, umami_bomb, fragrant_herbs,
  crispy_skin, smoky, tangy, peppery, earthy, briny, caramelized, herbal, nutty, silky)
- "confidence": 0.0-1.0

Dish: {name}
Description: {description}
Recent review excerpts: {reviews}
```

**Cost estimate:**
- One-time: ~500 dishes × SGD $0.02 = **SGD $10**
- Ongoing: SGD $0.05–0.20/day for new dish ingestion

## 5. Infrastructure & API

### 5.1 Architecture

```
React Native App
    │
    ├── hungryService.discovery.searchDishes()    ──► /recommendations/search
    ├── hungryService.discovery.decideForMe()     ──► /recommendations/decide
    └── hungryService.profile.updateInteraction() ──► /profile/taste/update
                    │
                    ▼
         Supabase Edge Functions (Deno)
                    │
          ┌─────────┼──────────────┐
          ▼         ▼              ▼
      pgvector   PostGIS       Redis (Upstash)
     (similarity)(proximity)   (TTL: 5 min)
```

**Why Edge Functions over a Python microservice:**
- Zero cold start (vs. Python container spin-up)
- Co-located with Postgres in the same region → pgvector latency ~5–20ms
- No VPC setup or separate deploy pipeline
- Swappable for a Python microservice if Phase 3 collaborative filtering needs matrix factorization at scale

### 5.2 API Endpoints

All endpoints map to the existing `HungryService` interface (`src/lib/services/types.ts`). No screen changes needed.

```
POST /functions/v1/recommendations/feed
  Authorization: Bearer {supabase_jwt}
  Body:     { lat, lng, limit?, excludeIds? }
  Response: { results: RecommendationResult[], profile_confidence: number }
  Target:   <1.5s P95

POST /functions/v1/recommendations/decide
  Authorization: Bearer {supabase_jwt}
  Body:     { lat, lng, radiusMeters?, excludeIds? }
  Response: { result: RecommendationResult }
           | { no_match: true, expand_options: [{ radiusMeters, count }] }
  Target:   <2s P95

POST /functions/v1/recommendations/search
  Authorization: Bearer {supabase_jwt}
  Body:     { query, tasteWeightOverride?, lat, lng, filters: SearchFilters }
  Response: { results: SearchResult[], total: number }
  Target:   <1s P95

POST /functions/v1/profile/taste/update
  Authorization: Bearer {supabase_jwt}
  Body:     { interactions: [{ dishId, action, rating?, dwellMs? }] }
  Response: { updatedVector: TasteVector, confidence: number, didChange: boolean }
  Target:   <500ms P95

GET  /functions/v1/profile/taste
  Authorization: Bearer {supabase_jwt}

```

### 5.3 Three-Tier Caching

```
Tier 1 — Zustand (client, already exists)
  Store:       useDiscoveryStore — holds last 20 recommendations in memory
  Latency:     0ms (no network)
  Invalidate:  profile update · app backgrounded >15 min · location shift >500m

Tier 2 — Redis / Upstash
  Key:         rec:{user_id}:{geo_cell_s2}
  TTL:         5 minutes
  Payload:     serialized RecommendationResult[20]
  Target hit:  ≥80% (users repeatedly query the same hawker centre)
  Cost:        ~SGD $0/month at launch volume

Tier 3 — pgvector HNSW
  Index:       vector_cosine_ops, ef_search=64 → 95%+ recall
  Pre-filter:  PostGIS narrows 100k dishes → ~500 candidates in 1–5ms
  Vector scan: HNSW on ~500 rows → 5–20ms
```

**`decideForMe` query plan:**

```
1. PostGIS proximity filter  →  ~50–200 candidates   (1–5ms)
2. pgvector HNSW ORDER BY   →  top 5                 (5–20ms)
3. Dietary flag join         →  removes 10–30%        (1ms)
4. Diversity post-processing →  in Edge Function      (1ms)
5. Serialize + return                                 (1ms)
──────────────────────────────────────────────────────────────
Cold path total:  ~10–30ms DB + ~10ms Edge overhead = <50ms
Redis cache hit:  ~5ms
```

### 5.4 Frontend Integration

The `HungryService` interface requires zero changes. The swap from mock to live is a single file:

```typescript
// src/lib/services/serviceProvider.ts  (create at Phase 2)
import { supabaseService } from './supabase/supabaseService';
export const hungryService = supabaseService;

// supabaseService.discovery.decideForMe() implementation:
async decideForMe(tasteProfile, lat, lng) {
  const { data } = await supabase.functions.invoke('recommendations/decide', {
    body: { lat, lng, radiusMeters: 500 }
  });
  return data.result?.dish ?? null;
}
```

Until this file is created, all screens continue calling `mockService` unchanged.
