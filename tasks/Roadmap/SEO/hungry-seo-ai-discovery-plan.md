# Hungry SEO + AI Discovery Plan

> Audience: Hungry product, engineering, marketing, and content teams
> Market focus: Singapore residents, Singapore-based diners, and visitors to Singapore
> Goal: Make Hungry discoverable through Google Search, Google AI features, ChatGPT Search, Claude web search, Gemini, and other AI-assisted discovery surfaces.

---

## 1. Executive Summary

Hungry should not optimize around the generic keyword “food app.” The stronger SEO and AI-search positioning is:

> **Hungry is the dish-level, location-aware food discovery layer for Singapore.**

The opportunity is to own searches like:

- “what to eat in Jurong East”
- “food near Jurong East MRT”
- “best chicken rice near me”
- “halal food near Orchard”
- “what to eat in Singapore for tourists”
- “hawker food under $6”
- “best food near Maxwell Food Centre”
- “vegetarian hawker food Singapore”

Google’s own SEO guidance says SEO is about helping search engines understand content and helping users decide whether to visit, not secret ranking tricks. Google also states there is no guaranteed way to rank first. Therefore, Hungry should focus on clean crawlable pages, useful Singapore-specific content, structured data, local intent, and visible data trust.

For AI discovery, the same foundations matter. Google says AI Overviews and AI Mode use the same core Search infrastructure and do not require special AI-only schema or machine-readable files. Instead, pages should be crawlable, textual, internally linked, useful, and supported by structured data that matches visible content.

### Core SEO Position

Hungry should become:

> **The most structured, local, dish-level food discovery database for Singapore.**

#### Singapore residents

Residents care about nearby food, price, opening hours, queue/wait time, open-now status, dietary needs, MRT proximity, lunch/dinner convenience, and neighbourhood relevance.

Visitors care about iconic dishes, first-time food guides, tourist-friendly hawker centres, MRT access, safety/confidence, opening hours, how to order, payment methods, and cultural explanations.

Example visitor queries:

- “what to eat in Singapore”
- “best hawker centres Singapore”
- “Singapore food guide first time”
- “food near Marina Bay Sands”

## 3. What Google Rewards

| Google principle | Hungry implementation |
|---|---|
| Help search engines understand content | Build crawlable public pages for areas, dishes, stalls, hawker centres, guides, and dietary pages. |
| Help users decide whether to visit | Provide real dish/stall data, price, opening hours, source/freshness, reviews, and nearby alternatives. |
| Logical site organization | Use clean directories: `/singapore/jurong-east/`, `/dishes/chicken-rice/`, `/hawker-centres/maxwell-food-centre/`. |
| Descriptive URLs | Use human-readable slugs, not opaque IDs. |
| Internal linking | Connect area → building → stall → dish → review → guide pages. |
| Structured data | Add JSON-LD for pages where facts are visible and verified. |
| Helpful content | Avoid thin AI-generated pages; publish only useful pages with enough real data. |
| Local relevance | Mirror local ranking factors: relevance, distance, prominence/popularity. |

## 4. AI Search and LLM Discovery Principles

AI search tools typically work by:

1. Understanding the user’s question.
2. Rewriting it into one or more search queries.
3. Retrieving candidate pages.
4. Extracting useful facts.
5. Synthesizing an answer.
6. Citing or linking to sources where the product supports it.

Google’s AI Mode and AI Overviews may use query fan-out, where the system issues multiple related searches across subtopics and data sources. That means Hungry should not rely on one generic page. It needs a network of interlinked pages that cover area, dish, venue, MRT, dietary, budget, and tourist-intent queries.

### What makes Hungry pages AI-citable?

Pages should include:

- short summary near the top
- clear headings
- factual tables
- visible source/freshness labels
- canonical URLs
- structured data
- internal links
- concise FAQ answers
- location-specific wording
- data-backed ratings/reviews only
- no hidden schema-only facts
- no fake trust claims

## 8. Structured Data Plan

Use JSON-LD and only mark up information that is visible on the page.

| Page | Structured data |
|---|---|
| Homepage | `Organization`, `WebSite`, `SoftwareApplication` |
| Area pages | `CollectionPage`, `ItemList`, `BreadcrumbList` |
| Hawker centre pages | `LocalBusiness` / `FoodEstablishment`, `ItemList`, `BreadcrumbList` |
| Stall pages | `Restaurant` / `FoodEstablishment`, `Menu`, `AggregateRating` only if real |
| Dish pages | `Product` or food-specific schema where suitable, `Review` only if real |
| Guides | `Article`, `FAQPage`, `BreadcrumbList` |
| Public user profiles | `ProfilePage` only if intentionally indexable |
| Reviews | `Review` only if original, visible, policy-compliant, and real |

Do not add:

- fake ratings
- fake review counts
- fake opening hours
- fake health/regulatory labels
- hidden schema facts not visible to users
- merchant-verified labels unless the merchant actually verified the data

## 15. Content Quality Rules

Hungry should enforce:

- Every page must answer a real user decision.
- Every rating/review count must be real.
- Every opening hour must have a source or “verify before going.”
- Every OCR/menu-derived item must be labelled unless verified.
- Every guide should have an author/editor or reviewer.
- Every area page should have enough data before indexing.
- Thin pages should be `noindex` until quality thresholds are met.
- Structured data must match visible page content.
- Do not publish programmatic pages with weak or duplicate content.
